## 0. 一句话版本

**API 进程只做四件事：读环境、装路由、装中间件、按清单拿资源。业务事实归 PostgreSQL，表结构归 `app-init`，Run 的执行归 worker。**

---

## 1. 进程分工：谁拥有什么

| 进程 | 入口 | 负责 | 不负责 |
|---|---|---|---|
| `api` | `backend/yuxi/api/main.py` | HTTP/SSE、鉴权、装配路由与中间件 | 建表、执行 Agent |
| `worker` | `backend/yuxi/workers/main.py` | 消费 ARQ、执行 Run、续租健康键 | 对外 HTTP |
| `app-init` | `backend/yuxi/bootstrap/app.py` | 迁移、内置定义与内置 Skill 同步 | 常驻服务 |
| `storage-init` | `docker/storage-init.sh` | 对象存储 bucket | 业务数据 |
| `frontend` | `frontend/` | 页面与调用封装 | 任何授权 |

这张表是后面所有"改代码去哪儿"判断的依据：**进程边界决定了模块归属**。表里的 ARQ、advisory lock、health key 等词，第 2 节有解释。

## 2. 术语表：先把黑话翻译成人话

后面每一节都会碰到这些词，这里先定性，读正文时就不用猜。

### 2.1 进程与队列

- **worker**：常驻后台进程，不开 HTTP 端口。它从 Redis 队列领取任务、执行 Agent Run。入口在 [`backend/yuxi/workers/main.py`](../../backend/yuxi/workers/main.py) 第 24-31 行。它和 `api` 是两个独立进程，所以 `/health` 返回 200 完全不代表 worker 活着。
- **ARQ**：Python 的 asyncio 任务队列库（async redis queue），broker 用 Redis。Yuxi 只把它当"投递—领取"的管道：投递在 [`backend/yuxi/modules/agents/services/transport.py`](../../backend/yuxi/modules/agents/services/transport.py) 第 36 行 `enqueue_job("process_agent_run", run_id, _job_id=f"run:{run_id}")`，消费端在 [`backend/yuxi/workers/settings.py`](../../backend/yuxi/workers/settings.py) 第 27-33 行的 `functions` / `cron_jobs` 里注册。`_job_id` 固定成 `run:{run_id}`，等于拿 Run id 当幂等键：任务还在队列里时，同一个 Run 不会被投第二次。
- **health key**：worker 周期性往 Redis 写一个带短 TTL 的键，`/ready` 读它判断"有没有活着的 worker"。worker 一停，键过期，`/ready` 立刻 503。
- **Redis**：只负责投递、短期事件、取消信号、缓存和健康键，不拥有业务事实。因为 `pending` Run 已经落在 PostgreSQL 里，Redis 抖一下可以补投，所以启动时 ping 失败只记 warning，不拦流量。

### 2.2 存储与一致性

- **PostgreSQL**：唯一业务事实来源，API 和 worker 读写同一个库。
- **advisory lock**：PG 的应用级互斥锁——不锁行、不锁表，只锁一个你命名的 key，谁先拿到谁进。`app-init` 用 `pg_advisory_lock(hashtextextended(:lock_scope, 0))` 保证"多副本同时启动时只有一个在跑迁移"（[`backend/yuxi/migrations/schema.py`](../../backend/yuxi/migrations/schema.py) 第 46 行加锁、第 52 行释放）。锁在数据库侧，所以跨容器也有效。
- **migration（迁移）**：改表结构的脚本。只有 `app-init` 执行；API 进程只用 `require_current_schema` 校验版本号，不建表。
- **checkpoint**：LangGraph 存的"图执行到第几步"的快照。Yuxi 只用 PG 存，所以 API 和 worker 能接着同一份状态续跑。

### 2.3 请求与启动

- **lifespan**：FastAPI 的启动/关停钩子。`startup` 抛错，应用就不会开始接流量；`finally` 里按逆序释放资源。
- **middleware（中间件）**：包在请求外面的层，请求进、响应出各穿一次。注意注册顺序和执行顺序相反（见 3.3）。
- **router / APIRouter**：一组接口的前缀分组，最后用 `include_router(..., prefix="/api")` 统一挂上去。
- **Depends（依赖注入）**：FastAPI 的"进视图前先跑这个函数"，鉴权和取当前用户基本都这么写。
- **readiness / liveness**：`/ready` 回答"能不能接流量"，`/health` 只回答"进程还在不在"。
- **SSE**：Server-Sent Events，服务端单向持续推送，聊天流式输出走它。
- **sandbox**：跑模型生成代码的隔离环境；`sandbox_provider` 是启动清单里的 required 项。
- **MCP**：Model Context Protocol，把知识库等能力按标准工具协议暴露给 Agent。

### 2.4 业务对象

- **Input**：用户提交的原始消息，先落 PostgreSQL，再由消费方转成正式 Message。
- **Turn**：一次完整往返——用户发一条，系统给出一个最终结果。
- **Run**：Turn 内的一次执行尝试，可重试；`pending` 表示"已登记、等 worker 领"。
- **lease / heartbeat**：Run 的执行权租约。worker 领到 Run 后定期续租；租约过期说明它死了，别的 worker 才能接手。
- **result_run_id**：Turn 的最终输出以它指向的那个顶层 Run 为准，不从相邻 Run 猜。

### 3.3 中间件：注册顺序 ≠ 执行顺序


```python
# backend/yuxi/api/main.py:161-176
# 访问日志记录请求处理时间；登录限流在外层先拦截，避免被限流请求进入业务日志。
app.add_middleware(AccessLogMiddleware)
app.add_middleware(LoginRateLimitMiddleware)


@app.middleware("http")
async def add_app_source_header(request: Request, call_next):
    """回显 API Key 绑定的调用来源，并禁止 OIDC 回调路径被缓存。"""
    response = await call_next(request)
    if request.url.path.startswith("/api/auth/oidc/"):
        response.headers["Cache-Control"] = "no-store"
        response.headers["Referrer-Policy"] = "no-referrer"
    app_id = getattr(request.state, "app_id", None)
    if app_id:
        response.headers["X-App-Id"] = app_id
    return response
```

Starlette 的 `add_middleware` 把新中间件插到列表**头部**，所以**最后注册的在最外层**。按 `117 → 162 → 163 → 166` 的注册顺序，实际请求穿过的顺序是：

```
请求 ─→ add_app_source_header ─→ LoginRateLimitMiddleware ─→ AccessLogMiddleware ─→ CORSMiddleware ─→ 路由
响应 ←──────────────────────────────────────────────────────────────────────────────────────────────┘
```

由此推论（都能在代码里验证）：

- 被登录限流 **429** 的请求**不会进访问日志**——[`access_log.py:44`](../../backend/yuxi/api/middleware/access_log.py) 是在 `await call_next(request)` 之后才写日志，外层提前 return 时它压根没被调用。
- `add_app_source_header` 是最外层，所以它看到的 `response` 已经过内层所有处理。

> 一句话：**写在后面的中间件，跑在前面。**

| 组件 | required | 失败后果 | 为什么 |
|---|---|---|---|
| `security_secrets` | 是 | 拒绝启动 | 没有它签不出/验不了 Token |
| `oidc_config` | 是 | 拒绝启动 | 登录方式依赖它 |
| `require_current_schema` | 是 | 拒绝启动 | Schema 版本不匹配时查询会静默出错 |
| `model_cache` | 是 | 拒绝启动 | 模型配置不可用则无法跑 Agent |
| `sandbox_provider` | 是 | 拒绝启动 | Run 无法安全执行 |
| `knowledge_base` | 是（仅知识开启） | 拒绝启动 | 关闭时只记 `disabled`，不失败 |
| **Redis** | **否** | **只记 warning** | 投递可恢复，见下节 |

**Redis 为什么特殊**：Input 与 Run 都先落 PostgreSQL，`pending` Run 就是"持久化的投递意图"，恢复扫描可以补投。所以 Redis 短暂不可用时，拒接流量只会把"投递延迟"升级成"整个服务不可用"，没有任何正确性收益。

另外，`required=True` 的判定标准是**操作抛异常**，不是返回值真假——见 [`bootstrap/api.py`](../../backend/yuxi/bootstrap/api.py) 第 105 行的 `_initialize_startup_component`。

## 5. `lifespan`：启动失败也要能收尾

```python
# backend/yuxi/api/lifespan.py:10-27
@asynccontextmanager
async def lifespan(app: FastAPI):
    """确保 startup 任意阶段失败时仍执行已取得资源的补偿清理。"""

    app.state.startup_complete = False
    app.state.startup_components = {}
    try:
        await startup(app)
        async with AsyncExitStack() as stack:
            knowledge_mcp = getattr(app.state, "knowledge_mcp", None)
            if knowledge_mcp is not None:
                await stack.enter_async_context(knowledge_mcp.manager.run())
            yield
    finally:
        app.state.startup_complete = False
        await shutdown_component("queue_clients", close_queue_clients)
        await shutdown_component("neo4j", close_neo4j_connection)
        await shutdown_component("postgres", pg_manager.close)
```

两个细节值得记：

- `finally` 里**先**把 `startup_complete` 置 `False`，**再**关闭资源。顺序反了，就会出现"资源已关、`/ready` 还报 ready"的窗口。
- 关闭顺序与启动顺序相反：`queue_clients → neo4j → postgres`。

## 6. `/ready` 到底由谁决定

```python
# backend/yuxi/api/routers/system.py:41-50
@system.get("/ready")
async def readiness_check(request: Request):
    """验证 API 接流量所需的启动状态与核心依赖。"""

    result = await get_readiness(
        startup_complete=bool(getattr(request.app.state, "startup_complete", False)),
        startup_components=getattr(request.app.state, "startup_components", None),
    )
    result["version"] = get_version()
    return JSONResponse(status_code=200 if result["status"] == "ready" else 503, content=result)
```

真正的判定：

```python
# backend/yuxi/modules/system/readiness.py:109-117
    checks = {
        "startup": {"status": "ok"} if startup_complete else {"status": "error", "code": "not_complete"},
        "postgres": postgres,
        "redis": redis,
        "worker": worker,
    }
    required_components_ready = all(component["status"] == "ok" for component in components.values() if component["required"])
    ready = all(check["status"] == "ok" for check in checks.values()) and required_components_ready
    degraded = any(component["status"] == "error" for component in components.values() if not component["required"])
```

四个 check 的性质不一样：

| check | 来源 | 说明 |
|---|---|---|
| `startup` | 内存里的 `app.state.startup_complete` | 只表示"装配跑完了" |
| `postgres` | 现场 `SELECT 1` | 2 秒超时 |
| `redis` | 现场 `PING` | 启动时只 warning，这里却是硬条件 |
| `worker` | Redis 里 3 个短 TTL 健康键 | worker 停止续租后，健康键一到 TTL 就 503 |

所以 `startup_complete = True` **不是总开关**，它只是四个条件之一。外面还有 1 秒缓存 + single-flight，防止探针被打爆。

> 注意这里的张力：启动时 Redis 挂了可以继续跑，但 `/ready` 会让它 503。前者是"允许起来"，后者是"别给它流量"——两件事，不矛盾。

## 8. 三个容易读反的地方

1. **中间件顺序**：文件里的先后是注册顺序，执行顺序相反。想"更早拦截"就**后注册**。
2. **`require_current_schema` 不建表**：它只校验版本。DDL 只有 `app-init` 在 advisory lock 里做。看到 "Schema" 相关代码先问"这是校验还是创建"。
3. **`/health` ≠ `/ready`**：`/health` 只证明进程活着；接流量看 `/ready`；业务正确性只能靠真实链路验证。

## 9. 架构不变量速记

这五条是读代码时的"否决权"：写法再顺，违反其中一条就是设计错了。

1. **路由薄**：HTTP 只做校验与转发；用例在 `services`，持久化查询在 `repositories`。
2. **PostgreSQL 是唯一业务事实 Owner**：Redis 只负责投递、事件、取消、缓存，不拥有 Run 的最终状态。
3. **`pending` Run 是持久化的投递意图**：`running` / `cancel_requested` 必须由唯一 attempt lease 拥有，心跳只有当前 owner 能续。
4. **Turn 结果只认 `result_run_id` 指向的顶层 Run** 及其 `output_message_id`；禁止从相邻 Run 或子 Run 猜输出。
5. **`/health` 只是 liveness；Schema 只由 `app-init` 改；权限的最终边界在后端 repository 的可见性查询**——前端守卫、prompt、UI 隐藏都不是授权。
